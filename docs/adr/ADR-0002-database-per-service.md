# ADR-0002: Database per Service

**Статус:** Принято

**Дата:** 05.08.2026

---

## Контекст

Проект **Tour Operator Platform** разрабатывается как микросервисная система, состоящая из нескольких независимых сервисов:

- User Service;
- Tour Service;
- Notification Service;
- API Gateway.

Каждый сервис отвечает за отдельную бизнес-область и должен иметь возможность независимо развиваться, масштабироваться и изменять свою внутреннюю реализацию.

Одним из важных архитектурных решений является определение способа хранения данных.

В монолитных приложениях часто используется подход **Shared Database**, когда все модули работают с одной общей базой данных.

Однако в микросервисной архитектуре такой подход создает сильную связанность между сервисами:

- сервисы начинают зависеть от структуры чужих таблиц;
- изменение схемы базы данных одного модуля может повлиять на другие сервисы;
- становится сложнее независимо разворачивать и масштабировать сервисы;
- нарушается принцип владения данными.

Для обеспечения независимости сервисов необходимо определить границы владения данными.

---

## Принятое решение

Для проекта выбирается архитектурный паттерн **Database per Service**.

Каждый микросервис владеет собственной базой данных и является единственным владельцем данных своей предметной области.

Сервисы не имеют прямого доступа к базам данных других сервисов.

Взаимодействие между сервисами осуществляется только через публичные интерфейсы:

- REST API;
- асинхронные сообщения;
- события.

Архитектура хранения данных:

```
                 Tour Operator Platform

                         |
        -----------------------------------------
        |                   |                   |
        ▼                   ▼                   ▼

  user-service       tour-service      notification-service

       |                  |                    |

       ▼                  ▼                    ▼

   user_db            tour_db          notification_db
```

Ответственность сервисов:

### User Service

Владеет данными:

- пользователей;
- ролей;
- учетных данных;
- информации для аутентификации.

Использует собственную базу данных:

```
user_db
```

---

### Tour Service

Владеет данными:

- туров;
- стоимости;
- продолжительности;
- доступности туров.

Использует собственную базу данных:

```
tour_db
```

---

### Notification Service

Владеет данными:

- уведомлений;
- истории отправки сообщений;
- шаблонов уведомлений.

Использует собственную базу данных:

```
notification_db
```

---

Каждый сервис самостоятельно управляет:

- схемой базы данных;
- миграциями;
- структурой таблиц;
- версиями данных.

Миграции выполняются независимо внутри каждого сервиса.

---

## Рассмотренные альтернативы

### 1. Shared Database (общая база данных)

При таком подходе несколько микросервисов используют одну общую базу данных.

Пример:

```
              PostgreSQL

                  |
    --------------------------------
    |              |               |

 user-service  tour-service  order-service
```

### Преимущества:

- простая начальная реализация;
- легко выполнять JOIN между таблицами разных модулей;
- проще выполнять транзакции между сущностями;
- меньше инфраструктуры.

### Недостатки:

- высокая связанность сервисов;
- изменение структуры таблицы может сломать несколько сервисов;
- невозможно независимо изменять модель данных;
- сложнее масштабировать отдельные сервисы;
- сервисы становятся зависимыми от одной точки хранения.

### Причина отказа:

Подход не соответствует принципам микросервисной архитектуры, где каждый сервис должен иметь собственную ответственность и автономность.

---

### 2. Database per Service

Каждый сервис использует собственную базу данных.

### Преимущества:

- независимость сервисов;
- изоляция данных;
- возможность использовать разные технологии хранения;
- независимое масштабирование;
- команды могут изменять модель данных без влияния на другие сервисы.

### Недостатки:

- невозможно выполнять обычные JOIN между сервисами;
- сложнее реализовывать распределенные транзакции;
- требуется обмен данными через API или события;
- увеличивается количество инфраструктурных компонентов.

### Причина выбора:

Данный подход лучше соответствует целям проекта и обеспечивает необходимую автономность микросервисов.

---

## Последствия

### Положительные последствия

- Каждый сервис имеет четкую ответственность за свои данные.
- Сервисы могут независимо развиваться и разворачиваться.
- Изменения структуры одной базы данных не влияют напрямую на другие сервисы.
- Упрощается масштабирование отдельных компонентов системы.
- Архитектура соответствует принципам Domain-Driven Design (Bounded Context).
- Возможно использование различных технологий хранения данных для разных сервисов.

---

### Отрицательные последствия

- Увеличивается сложность системы хранения данных.
- Нельзя использовать прямые SQL JOIN между сервисами.
- Требуется проектировать взаимодействие между сервисами через API или события.
- Распределенные транзакции становятся сложнее.
- Возникает необходимость решения вопросов согласованности данных.
