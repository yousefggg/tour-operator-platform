# ADR-0001: Выбор Hexagonal Architecture

**Статус:** Принято

**Дата:** 05.08.2026

---

## Контекст

Проект **Tour Operator Platform** разрабатывается как современная микросервисная система. В перспективе платформа будет состоять из нескольких независимых сервисов (User Service, Tour Service, Notification Service и других), взаимодействующих между собой посредством HTTP и асинхронного обмена сообщениями.

Основной задачей архитектуры является обеспечение независимости бизнес-логики от используемых технологий. Бизнес-правила не должны зависеть от Spring Boot, Spring Data JPA, PostgreSQL, RabbitMQ, Kafka или других инфраструктурных компонентов.

При использовании классической многослойной архитектуры (Layered Architecture) бизнес-логика со временем начинает зависеть от фреймворков и библиотек. Это приводит к высокой связанности компонентов, усложняет тестирование и затрудняет замену инфраструктурных решений.

Для данного проекта требуется архитектурный подход, который позволит:

- изолировать бизнес-логику от инфраструктуры;
- обеспечить слабую связанность между слоями приложения;
- упростить модульное тестирование;
- обеспечить возможность замены технологий без изменения доменной модели;
- сохранить архитектуру понятной и масштабируемой по мере роста проекта.

---

## Принятое решение

В качестве основной архитектуры всех backend-сервисов проекта выбрана **Hexagonal Architecture (Ports & Adapters)**.

Каждый сервис строится вокруг доменной модели, которая является центральной частью приложения и не зависит от внешних технологий.

Взаимодействие между доменом и внешним миром осуществляется исключительно через порты (Ports), представленные интерфейсами.

Работа с инфраструктурой выполняется адаптерами (Adapters), реализующими соответствующие порты.

В проекте используются следующие принципы:

- бизнес-логика располагается в слое Domain;
- сценарии использования реализуются в слое Application;
- взаимодействие с базой данных, очередями сообщений и внешними сервисами выполняется слоем Infrastructure;
- все зависимости направлены в сторону домена;
- инфраструктура зависит от домена, а не наоборот.

---

## Рассмотренные альтернативы

### 1. Layered Architecture

**Преимущества**

- простая структура проекта;
- невысокий порог входа;
- подходит для небольших приложений.

**Недостатки**

- бизнес-логика постепенно начинает зависеть от Spring и JPA;
- сложнее заменить инфраструктурные технологии;
- тестирование часто требует запуска Spring Boot и базы данных.

**Причина отказа**

Архитектура недостаточно хорошо подходит для проекта, который планируется развивать как микросервисную систему.

---

### 2. Clean Architecture

**Преимущества**

- строгая изоляция бизнес-логики;
- высокая тестируемость;
- соблюдение принципа Dependency Inversion.

**Недостатки**

- более сложная структура;
- больше уровней абстракции;
- избыточна для текущего масштаба проекта.

**Причина отказа**

Hexagonal Architecture обеспечивает необходимую степень независимости при меньшей сложности реализации.

---

## Последствия принятого решения

### Положительные

- доменная модель не зависит от Spring Framework;
- инфраструктурные технологии можно заменить без изменения бизнес-логики;
- упрощается написание модульных тестов;
- уменьшается связанность компонентов;
- архитектура лучше подходит для микросервисов;
- упрощается сопровождение проекта.

### Отрицательные

- увеличивается количество интерфейсов и классов;
- возрастает сложность структуры проекта;
- требуется понимание принципов Ports & Adapters;
- разработка занимает больше времени по сравнению с простой многослойной архитектурой.

---

## Правила реализации

Для каждого backend-сервиса используется следующая структура:

```
domain/
application/
infrastructure/
config/
```

- Все порты объявляются в доменном или прикладном слое.
- Все адаптеры располагаются в инфраструктурном слое.
- Контроллеры являются Primary (Inbound) Adapter.
- Репозитории, клиенты внешних сервисов и отправители сообщений являются Secondary (Outbound) Adapter.
- Доменный слой не должен содержать зависимостей от Spring Framework, JPA, Hibernate и других инфраструктурных библиотек.

---

## Заключение

Hexagonal Architecture выбрана в качестве основной архитектуры проекта, поскольку она обеспечивает независимость бизнес-логики от инфраструктуры, улучшает тестируемость приложения и позволяет развивать систему без жесткой привязки к конкретным технологиям.
